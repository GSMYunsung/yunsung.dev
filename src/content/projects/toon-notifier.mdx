## 만든 이유

인스타그램에서 재미있는 인스타툰을 발견해도, 다음 편이 올라왔는지 확인하려면 **직접 그 계정을 방문해야 합니다.** 인스타그램의 일반 팔로우 알림은 팔로우한 모든 계정의 게시물이 섞여 오기 때문에 툰 업데이트만 골라서 받는 방법이 없었습니다. 여러 작가를 팔로우하면 새 편이 언제 올라왔는지 놓치기 쉽고, 결국 구독하던 시리즈를 잊어버리게 됩니다.

관심 작가를 등록해두면 **새 에피소드가 올라올 때 알림을 받을 수 있는 앱**을 만들었습니다.

## 주요 기능

- **인스타툰 구독 관리** — 마지막으로 읽은 화의 인스타 링크를 붙여넣으면 계정명·시리즈명·화수를 자동 파싱. 스와이프 삭제, 수정 지원
- **자동 에피소드 감지** — 최신 게시물 12개를 최신순으로 스캔해 캡션 키워드 매칭으로 새 화 감지. 캡션에 화수가 없을 경우 OCR.space API로 이미지에서 직접 인식
- **OCR 캐싱** — `post.id` 기반 AsyncStorage 캐시로 동일 포스트 반복 API 호출 방지
- **복수 화수 동시 알림** — 한 사이클에 여러 화가 올라온 경우 "3화, 4화가 추가되었어요" 형식으로 한 번에 알림
- **에피소드 목록** — 카드 탭 시 읽은 화·신규화 목록 아코디언 펼치기. 화수 탭 → 해당 인스타 게시물로 이동 + 읽음 자동 처리
- **직접 확인 배지** — 최신 12개 게시물 안에서 시리즈를 감지하지 못한 경우 직접 확인 배지 표시
- **완결 자동 처리** — `완` / `완결` 패턴 감지 또는 3주 이상 새 포스트 없으면 완결로 처리
- **푸시 알림** — 새 에피소드 발견 시 Expo Push API로 즉시 푸시 알림 전송
- **읽음 처리** — 화수별 읽음 상태 관리, NEW 배지 표시
- **라이트 / 다크 모드** — 시스템 기본값 연동 및 수동 전환

## 서비스 흐름

```
📱 앱 (Expo)
  │  앱 실행 시 Expo push token → Supabase 저장
  │  툰 추가/삭제/읽음 처리 → Supabase 동기화
  ▼
🗄️ Supabase (온라인 DB)
  │  toons 테이블: 등록된 툰 목록
  │  push_tokens 테이블: 디바이스 푸시 토큰
  ▼
⚙️ GitHub Actions (3시간마다 자동 실행)
  │  Supabase에서 툰 목록 읽기
  │  hasdata API로 인스타 최신 게시물 12개 조회
  │  캡션 키워드 매칭 + OCR 폴백으로 새 화 감지
  │  새 편 발견 시 Expo Push API로 알림 전송
  ▼
📳 폰에 푸시 알림 도착
```

## 감지 엔진

**캡션 + OCR 2단계 에피소드 감지**

캡션에 화수 표기가 없는 경우를 대비해 **2단계 폴백 구조**를 설계했습니다. 먼저 캡션에서 `n화` / `n편` / `ep.n` / `#n` 패턴으로 화수를 추출하고, 캡션에 화수가 없으면 OCR.space API로 게시물 이미지에서 텍스트를 인식해 화수를 뽑아냅니다. 앱과 GitHub Actions 서버 모두 동일한 매칭 유틸(`matchingUtils.js`)을 공유해 감지 로직의 단일 진실 공급원을 유지했습니다.

캡션 매칭에는 시리즈명에서 3자 이상인 단어를 우선 사용해 짧은 단어로 인한 오탐을 방지했고, OCR 결과는 `post.id`를 키로 AsyncStorage에 캐싱해 동일 포스트에 대한 반복 API 호출을 막았습니다.

**OCR 호출 93% 절감 — `last_post_id` 기준점 설계**

초기에는 GitHub Actions가 실행될 때마다 최신 포스트 12개 **전체를 처음부터 재검사**했습니다. 새 포스트가 없어도 매 사이클마다 OCR을 최대 12회씩 소모하는 구조였습니다.

Supabase `toons` 테이블에 `last_post_id` 컬럼을 추가해 **마지막으로 처리한 포스트 ID를 기억**하고, 그 이후 포스트만 처리하도록 변경했습니다.

첫 체크 시 기준점을 **가장 오래된 포스트(oldest)** 로 설정하는 것도 중요했습니다. newest 기준으로 잡으면 등록 당시 이미 나와있던 이전 화들을 영원히 놓치는 버그가 생깁니다. 이 케이스를 포함해 회귀 테스트 4개로 동작을 고정했습니다.

**GitHub Actions 배치 + Expo Push 알림 파이프라인**

별도 서버 없이 **GitHub Actions를 3시간 인터벌 배치 서버로 활용**했습니다. 배치 스크립트가 Supabase에서 구독 목록과 push token을 읽어 인스타그램 최신 12개 게시물을 확인하고, 새 에피소드가 감지되면 Expo Push API로 해당 디바이스에 알림을 전송합니다. 이미 `hasNewEpisode: true`인 경우 중복 알림을 차단하는 로직도 포함했습니다.

**AsyncStorage + Supabase 이중 저장 구조**

오프라인 환경에서도 앱이 동작하도록 **로컬은 AsyncStorage, 온라인 동기화는 Supabase**로 이중 저장 구조를 설계했습니다. 앱이 포그라운드로 돌아올 때 배치 스크립트가 Supabase에 기록한 새 에피소드 정보를 로컬 상태에 반영해, 알림을 못 받았더라도 앱을 열면 업데이트가 표시됩니다.

**다음 화 순차 네비게이션**

새 에피소드가 여러 화 쌓인 경우 **안 본 화를 화수 오름차순으로 정렬해 한 화씩 순서대로 이동**하도록 설계했습니다. 카드를 탭할 때마다 `readEpisode`가 1씩 증가하고, 모두 소진하면 `hasNewEpisode`가 `false`로 전환됩니다.

## AI 협업 워크플로우

1인 개발임에도 서비스 레이어 분리·OCR 최적화·버그 수정·배포 자동화를 짧은 기간 안에 완성할 수 있었던 건, Claude Code를 단순한 코드 생성 도구가 아닌 **제약이 걸린 협업 구조** 안에서 운용했기 때문입니다.

**CLAUDE.md — AI에게 건네는 업무지시서**
기술 스택, 파일 구조, API 응답 형태, "OTA는 JS 변경만, 네이티브 변경은 새 빌드" 같은 배포 규칙까지 문서로 고정했습니다. 대화가 끊겨도 AI가 같은 제약 안에서 동작하도록 컨텍스트를 유지하는 장치입니다.

**제약 걸기 + 수기 검증**
작업을 넘길 때는 반드시 실패 조건을 먼저 명시했습니다. AI가 생성한 코드는 "이 로직 어떻게 동작하는지 설명해줘"를 먼저 요청한 뒤 이해한 뒤에야 반영했습니다. AI가 생성했더라도 제가 이해하지 못한 코드는 배포하지 않는다는 원칙이었습니다.

**TROUBLESHOOTING.md — 오류를 자산으로**
버그가 해결될 때마다 "무엇을 고쳤나"가 아니라 "왜 틀렸나"를 기록했습니다. 진단 과정 전체를 남겨 비슷한 증상이 다시 생겨도 같은 삽질을 반복하지 않도록 했습니다. 현재 7개 케이스가 쌓여 있습니다.

**테스트 자동화 후 배포**
새 로직은 반드시 테스트를 먼저 작성했습니다. `filterNewPosts` 도입 시 16개 케이스(첫 등록, 이미 처리한 포스트, 신규 없음, 복수 신규 등 경계 조건 포함)를 전부 통과시킨 뒤 GitHub Actions에 반영했습니다.

## 트러블슈팅

### OCR 무료 한도 소진 → 캐싱으로 해결

초기에 OCR.space API를 호출할 때마다 크레딧이 소모되어 무료 한도가 빠르게 소진됐습니다. 문제는 동일한 포스트를 매 사이클마다 다시 OCR하는 구조에 있었습니다.

`post.id`를 키로 AsyncStorage에 OCR 결과를 캐싱해, 한 번 인식한 포스트는 다시 API를 호출하지 않도록 처리했습니다. `last_post_id` 기준점 설계와 함께 적용하니 OCR 호출이 **93% 절감**됐습니다.

---

### ML Kit 온디바이스 OCR 도입 → 인식률 한계로 철회

ocr.space API 무료 한도 소진 문제를 근본적으로 해결하기 위해 네트워크 없이 디바이스에서 직접 실행되는 ML Kit 온디바이스 OCR을 도입했습니다.

결과는 실망스러웠습니다. 일반 명조·고딕 폰트에서는 인식률이 85% 이상이었지만, 인스타툰 썸네일에서 주로 쓰이는 **아트체·손글씨 폰트에서는 30~40% 수준**으로 떨어졌습니다. "47화" 같은 단순한 숫자조차 "4화", "41화", 인식 실패로 분산됐고, 이미지 전처리(1080px 리사이즈), 신뢰도 임계값 조정 등을 시도했지만 개선 폭이 10% 내외에 그쳤습니다. ocr.space Engine 2가 동일 이미지에서 70% 이상 인식하는 것과 비교해 격차가 명확했습니다.

API 호출 없는 장점보다 **인식 실패로 인한 오감지 비용이 더 컸기** 때문에 ocr.space API로 되돌아갔습니다. 대신 `last_post_id` 기준점 + AsyncStorage 캐싱으로 API 호출 자체를 93% 줄여 한도 문제를 해결했습니다.

---

### 매칭 로직 오탐 버그 4건 연속 수정

OCR 엔진 교체 이후 매칭 로직에서 오탐이 연속으로 발견됐습니다. 증상은 달랐지만 원인은 하나였습니다 — **조건이 너무 느슨했습니다.**

- `isCompleteEpisode(ocrText)` 단독으로 OCR 매칭이 통과돼, "완결" 글자만 있는 무관한 이미지가 새 화로 인식됨
- `keyWords=[]`일 때 `minMatch=0`이 되어 모든 캡션이 매칭됨
- 완결 감지 시 키워드 1개만 있어도 통과하는 느슨한 분기가 오탐 경로로 작동
- 캡션은 `minMatch=2` 기준인데 OCR은 1개만 있어도 통과 — OCR이 우회 경로가 됨

모두 `keyWords.length > 0` 가드 추가 + `minMatch` 기준 일원화로 해결했습니다.

---

### 앱·서버 매칭 로직 이중화 → 단일 소스 통일

위 버그들을 앱(`check-service.js`)에서 수정했는데, 서버(`check-toons.js`)는 수정 전 로직으로 계속 동작하고 있었습니다. 앱에서 3편만 감지할 때 서버는 5편을 감지하는 불일치가 생겼습니다.

공통 매칭 로직을 `src/utils/matchingUtils.js`로 추출해 앱과 서버 모두 이 파일을 참조하도록 통일했습니다. 같은 로직을 두 곳에 따로 작성하면 반드시 한 쪽이 뒤처진다는 교훈을 CLAUDE.md 규칙으로 추가했습니다.

### 개발 빌드 Metro 서버 localhost 문제

ML Kit 같은 네이티브 모듈은 Expo Go에서 동작하지 않아 개발 빌드가 필요했습니다. EAS로 dev 빌드를 올리고 Metro 서버에 연결하려는데 `localhost:8081`로 고정되어 폰에서 접근이 불가했습니다.

`--host lan` 옵션, 환경변수 설정, 핫스팟 등 여러 방법을 시도했으나 모두 실패했습니다. 원인은 **프로젝트 루트에 `ios`/`android` 폴더가 존재**하면 Expo CLI가 로컬 네이티브 빌드 환경으로 인식해 localhost를 사용하는 것이었습니다. 두 폴더를 삭제하니 올바른 LAN IP로 URL이 생성됐습니다.

```bash
rm -rf ios android
npx expo start --dev-client
# → exp+toonify://expo-development-client/?url=http://192.x.x.x:8081
```

EAS Build를 사용하는 경우 로컬에 `ios`/`android` 폴더가 없어도 무방합니다. 네이티브 모듈 변경 시에만 `eas build --profile development`로 새 바이너리를 빌드하고, 이후 JS 수정은 Metro Fast Refresh로 즉시 반영됩니다.
